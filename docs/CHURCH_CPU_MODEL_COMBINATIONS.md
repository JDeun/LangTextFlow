# Church CPU Korean → English model-combination experiment

Tracking: [#118](https://github.com/JDeun/LangTextFlow/issues/118),
[#117](https://github.com/JDeun/LangTextFlow/issues/117),
[#106](https://github.com/JDeun/LangTextFlow/issues/106),
[#107](https://github.com/JDeun/LangTextFlow/issues/107).

## Why a new experiment

A real TranslateGemma 4B + faster-whisper CPU benchmark produced translated
caption p95 ~10.99 seconds and total RTF ~1.18 **after fixing a JSON metadata
leak**. Term accuracy was ~78% on synthetic samples. RTF >1 fails sustained
realtime throughput. CI success is *not* an acceptable translation.

The immediate hypothesis is a dedicated small encoder-decoder MT runtime:
CTranslate2 CPU INT8 instead of 4B general-model decoding.

| Korean ASR | Korean → English MT | First target | Caveat |
|---|---|---|---|
| Qwen3-ASR 0.6B INT8 | OPUS-MT ko-en (CT2 INT8) | 8GB PC | Utterance-only ASR is not native streaming |
| Korean Zipformer INT8 | OPUS-MT ko-en (CT2 INT8) | 8GB PC | Faster partial ASR may sacrifice accuracy |
| Qwen3-ASR 0.6B INT8 | OPUS-MT tc-big ko-en (CT2 INT8) | 16GB reference | Higher-resource comparison |
| Korean Zipformer INT8 | OPUS-MT tc-big ko-en (CT2 INT8) | 16GB reference | Quality/latency trade-off |

The previous 3-clip ASR-only FLEURS evaluation reported 0.6B Qwen CER ~0.0554
and Zipformer CER ~0.1641. This small sample is not an actual sermon-quality
score. Neither is certified at any memory tier.

## Model provenance and licensing

- `Helsinki-NLP/opus-mt-ko-en` on Hugging Face: Apache-2.0 weights.
- `Helsinki-NLP/opus-mt-tc-big-ko-en`: CC BY 4.0; attribution required.
- CTranslate2: CPU INT8 and standard MarianMT tokenization/conversion.
- Qwen3-ASR: licensed/model-revision checks from the existing #116 harness.
- Streaming Korean Zipformer: native online ASR, licensed weights and SHA
  recorded by the existing pinned-release provisioner.
- NLLB-200-distilled-600M is CC BY-NC 4.0: **research-only, not an unconditional
  product distribution candidate**.

Every GitHub Action run resolves the Hugging Face repository to an **exact
commit SHA, records it in model-revision.json, downloads exactly that SHA,
and records the converted INT8 file hashes**. Before declaring a reproducible
deployment winner, transfer the selected exact SHA into a fixed model lock
and rerun; moving upstream `main` is not a production pin.

## Evidence generated by the opt-in workflow

`church-cpu-opus-mt.yml` runs two independent jobs (small and big MT).
Each job records:

1. CPU model, cores, RAM and disk, plus model repository SHA/license.
2. Real Marian model converted and loaded by CTranslate2 INT8.
3. Sixteen existing synthetic ko→en cases from the **unchanged** 20-case
   benchmark: output validation, synthetic chrF++, critical-term misses,
   per-item latency and p95.
4. Actual pinned FLEURS Korean read-speech replay (same 3 IDs/PCM SHA) for
   Qwen3-ASR 0.6B and Korean Zipformer with MT **resident at the same time**:
   source CER/WER, translated coverage, sequential playback RTF, estimated
   lag and sampled Python + child-process peak RSS.
5. Full inference JSON, model hashes and failure logs, even if one candidate
   errors. The job fails if required candidates are not successfully run.

Important distinction: the three-clip combination test is **sequential
utterance replay**, not LangTextFlow's full live CaptionRuntime, nor a
continuous 60-minute load test. It lacks independent human English references
for the real speech. Peak RSS is measured on a nominal ~16GB hosted runner and
does not prove 4GB/8GB physical support. For an actual verdict we must replay
the selected combo through live CaptionRuntime with bounded queues and stale
revision cancellation.

## Deployment acceptance — not met by this PR

- No silent JSON/context leak, no stale or source-language-only strings
  marked as successfully translated English.
- Independently reviewed sermon/church passages including negation,
  Bible-book and verse references, numbers and names; blinded bilingual
  errors documented alongside chrF and CER. Synthetic references alone fail.
- End-to-end translation queue stays bounded. **Sustained RTF <1** on
  physical hardware with margin for other processes; delivery p95 target
  should be determined with worship operators, provisionally <3 seconds.
- Exact same licensed audio/audio SHA across models, matched microphone
  and church soundboard conditions, dropout/recovery testing.
- 30, 60 and 90-minute offline sessions on physical donated-class **8GB CPU
  Windows/Linux** first, with peak total RAM/swap and thermal metrics.
  Attempt 4GB only after 8GB translation is actually supported and stable.
- Check model licenses/third-party notices before any distributable build.

**Nothing in the benchmark changes LangTextFlow's production translation
provider or automatically selects models for a real congregation.**
