# 교회 통역 품질 기준 — 자원 절감 이전 검증

## 원칙

교회·선교·지역 공동체에서 저가의 CPU PC로 사용하려는 목적은 유지합니다.
다만 **사용 가능한 통역 품질을 먼저 얻고, 이후 하드웨어를 줄여도 품질이
허용 범위를 벗어나지 않도록 검증**하는 순서로 개발합니다.

"완벽한 번역"은 모든 방언·음질·교리적 문맥에서 증명 가능한 상태가 아닙니다.
실제 목표는 원문의 **의미·부정·수치·성경 장절·인명·신학적 개념**을
허용 가능한 오류율과 지연으로 전달하는 것입니다.

## 1차 기준 장비 — GitHub Actions

| 항목 | 표준 공개 저장소 `ubuntu-latest` |
|---|---|
| CPU | 4 vCPU |
| 메모리 | 16 GB |
| 디스크 | 14 GB SSD |
| GPU | 없음 |
| 모델 | CPU 양자화 TranslateGemma 4B |
| 음성 입력 | 이 단계는 미사용 — **이상적인 원문 텍스트만** |
| 번역 | ko→en 및 en→ko, 20개 자체 작성 합성 사례 |

실제 CPU SKU, 디스크 여유, cgroup·메모리 정보는
`church-translation-hardware.txt`에 기록합니다. 가상 머신 간 성능 편차가
있으므로 nominal 4 vCPU와 동일한 클럭·IPC·속도를 가정해서는 안 됩니다.

워크플로: [Church translation quality](../.github/workflows/church-translation-quality.yml).

## 기준을 확정하기 전 필요한 검증

1. **번역 모델 단독 품질:** 표준 입력문을 TranslateGemma에 제공하고 출력 전체,
   chrF++, 용어 일치율, p50/p95 지연·실패를 기록합니다.
2. **검수된 정답셋:** 현재 `benchmarks/church_translation_quality.v1.jsonl`은
   **합성·사람 독립 검수 미완료** 자료입니다. 각 번역을 한국어·영어에 능숙한
   검수자가 확인하고 의미·부정·장절 오류를 유형별로 판정해야 합니다.
   종교적 해석이 갈릴 수 있는 사례는 맥락을 함께 기록합니다.
3. **ASR+번역 통합 품질:** 동일한 음원을 STT→번역에 통과시키며 원문 ASR 오류가
   실제 통역에 어떻게 전파되는지 분리해 측정합니다.
   #101에서 발견된 높은 한국어 오류율은 아직 해결되지 않았습니다.
4. **실시간성:** 연속된 설교 음성이 들어오는 상태에서 처리 지연·큐 증가·출력
   누락·자막 시간차를 확인합니다. 단일 번역 응답 성공만으로 실시간 통역을
   합격 처리하지 않습니다.
5. **현장 승인:** 검수된 품질 기준과 30/60/90분 연속 운용을 함께 통과하고,
   예배 담당자와 함께 받아들일 수 있는 지연과 오류 기준을 확정합니다.

## 그다음에만 장비 사양 축소

확정한 모델·검수셋·오디오 SHA와 기준 번역 결과를 고정한 뒤
16GB → 8GB → 4GB 순서로 최적화합니다.

- 작은 모델, INT8/INT4 양자화, 추론 스레드, chunk/batch, 번역 큐를 **한 변수씩** 바꿉니다.
- 모든 변경마다 원본과 동일한 평가셋으로 chrF++, 핵심 용어 누락, 인간 의미 평가,
  p95 자막 지연, peak RSS, OOM·swap, 중단·복구를 교차 비교합니다.
- 속도가 빨라도 의미가 반대로 바뀌거나 중요 신학 용어가 누락된다면
  **성능 개선으로 간주하지 않습니다.**
- 4GB/8GB는 아직 목표 테스트 단계입니다. 공식 최소 사양으로 보증하지 않습니다.
